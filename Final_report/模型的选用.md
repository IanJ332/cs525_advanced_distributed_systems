# **模型选型调研报告：基于分布式推理集群的灰色故障动机实验**

## **1. 实验背景与动机的深刻剖析 (Context and Motivation Deep Dive)**

在现代云计算与分布式边缘计算架构中，深度神经网络（DNN）推理集群的可靠性保障正面临前所未有的挑战。传统的集群高可用性（High Availability, HA）架构主要依赖于 L4/L7 负载均衡器（例如 HAProxy 或 Nginx）来进行节点健康检查。然而，大量顶级学术研究与生产环境的实际案例表明，现代分布式系统中最致命的威胁不再是显式的"崩溃停止"（Fail-stop）故障，而是隐蔽的"灰色故障"（Gray Failures）或"慢化故障"（Fail-slow）。

灰色故障的核心特征在于其"差异性可观测性"（Differential Observability）。当底层硬件（如 CPU、内存控制器或 L3 Cache）遭遇局部资源争抢、微架构老化或热降频时，节点并未彻底宕机。此时，传统的 HAProxy 探针（通常是简单的 TCP 握手或轻量级的 HTTP GET /health 请求）仍能迅速得到响应，因为这些操作占用的 CPU 周期和内存带宽微乎其微，轻易就能在操作系统调度的时间片中完成。因此，负载均衡器依然将该节点标记为"健康"状态，并持续向其路由高强度的推理请求。

然而，对于驻留在该节点上的 Triton Inference Server 及其承载的重度依赖计算和内存的 DNN 模型而言，这种微架构级别的资源受限是毁灭性的。模型的长尾延迟（P99 Latency）会呈现指数级的恶化，导致整个分布式推理集群的吞吐量崩溃，进而引发级联效应并违反服务等级协议（SLO）。

UIUC CS525 课程 "GrayPulse" 项目的动机实验（Motivation Experiment）正是为了在受限环境中精确复现并科学地测量这一现象。本次实验被设定在一个极度受限的沙盒环境中：每个推理节点仅配备 2 核 Intel Cascade Lake CPU（无物理 GPU）、22MB L3 Cache、7.5GB 内存以及 32GB 磁盘。本报告作为该实验的首席指导文件，旨在从计算机体系结构与深度学习系统（ML Systems）交叉的视角，为 Triton Inference Server 挑选最完美的基准 DNN 模型。我们将坚守"化繁为简"（start simple）的研究准则，排除参数量过于庞大且难以在 7.5GB 内存下稳定运行的大语言模型（LLM），专注于经典的计算机视觉（CV）与自然语言处理（NLP）模型。通过严谨的硬件兼容性评估、微架构干扰敏感度推演以及工程落地性论证，本报告将构建一套无懈可击的实验方案，以无可辩驳的延迟退化数据向学术界展示灰色故障的破坏力。

## **2. 目标硬件微架构特性与约束边界分析 (Microarchitectural Analysis and Constraints)**

模型选型的第一步，是深刻理解模型计算图（Computation Graph）与目标硬件微架构之间的交互机制。本节将对给定的 2 核 Intel Cascade Lake 处理器及其内存子系统进行详尽的剖析。

### **2.1 Intel Cascade Lake 架构与 AVX-512 VNNI 指令集**

Intel Cascade Lake 是 14 纳米工艺下的服务器级微架构，其最大的亮点之一是引入了 Intel Deep Learning Boost 技术，特别是包含向量神经网络指令集（Vector Neural Network Instructions, AVX-512 VNNI）。在缺乏物理 GPU 的环境中，CPU 进行 DNN 推理严重依赖于其浮点运算单元（FPU）和宽向量寄存器。AVX-512 VNNI 能够将原本需要多条指令完成的乘加运算（FMA）融合为单条指令（例如 VPDPBUSD 操作），极大地加速了密集矩阵乘法（GEMM）的效率。

然而，这种强大的计算能力是一把双刃剑。512 位的超宽寄存器在进行上下文切换（Context Switch）时，需要操作系统保存和恢复庞大的寄存器状态，这带来了极高的微架构惩罚。在仅有 2 个物理核心的系统中，如果引入额外的干扰进程，Triton Inference Server 的工作线程将频繁被剥夺执行权，导致极其严重的调度延迟和上下文切换开销。

### **2.2 非包含式 L3 Cache 层级与内存带宽**

Cascade Lake 架构对缓存层级进行了重大重新设计，采用了非包含式（Non-inclusive）的受害者缓存（Victim Cache）架构。在该架构中，每个核心拥有 1MB 的私有 L2 Cache，而 L3 Cache 则是所有核心共享的。22MB 的 L3 Cache 对于仅有 2 个核心的系统而言，人均可用容量极高。

这种大容量的共享 L3 Cache 对 DNN 推理意味着：在无干扰的稳态下，许多中小型模型（如 ResNet-50 或轻量级 BERT）的权重参数和瞬态特征图（Feature Maps/Activations）可以高比例地驻留在 L3 Cache 中，缓存命中率（Cache Hit Rate）极高，从而掩盖了 DDR4 内存的高延迟。但是，共享 L3 Cache 也是整个微架构中最脆弱的环节。一旦恶意或失控的后台进程（如 stress-ng --cache）大量分配并随机读写内存，L3 Cache 中的 DNN 数据将被迅速驱逐（Eviction）。此时，CPU 被迫跨越缓存层级，前往延迟高达 200 个时钟周期以上的 DRAM 抓取数据，导致内存带宽（Memory Bandwidth）饱和，推理延迟将发生断崖式下跌。

### **2.3 严苛的 7.5GB 内存容量约束**

系统物理内存被严格限制在 7.5GB。在实际部署中，Linux 操作系统内核本身将占用约 1GB 左右的内存，Triton Inference Server 框架及其底层依赖（如 gRPC/HTTP 服务器、共享内存管理器等）会占用数百兆字节。此外，深度学习框架在加载模型时往往会进行内存预分配机制（例如构建计算图、分配输入/输出张量的显式内存池等）。

因此，留给 DNN 模型权重（静态内存）和推理时产生的中间激活值（动态内存）的实际可用空间非常有限（安全阈值应控制在 3GB 以内）。如果选用内存占用过大的模型，一旦受到 stress-ng 干扰导致内存碎片化加剧，极易触发 Linux 内核的 OOM（Out-Of-Memory）Killer 机制，这会直接导致 Triton 进程被强制终止（Fail-stop），从而破坏了我们旨在展示"慢化故障"（Fail-slow）的实验初衷。模型必须足够精简，以确保即使在极端压力下，系统依然能保持残喘运行，完美呈现 P99 延迟的爆炸性增长。

## **3. 候选经典 DNN 模型的深度横向对比 (Candidate Model Comparison)**

基于硬件极度受限（特别是 7.5GB 内存限制）的考量，大语言模型（如 Llama、GPT 系列）因其动辄数十 GB 的显存/内存需求被直接排除在外。为了遵循"化繁为简"的方法论，我们将目光投向了参数量适中、架构成熟且计算特征鲜明的经典模型。在此，我们分别从计算机视觉（CV）和自然语言处理（NLP）领域挑选了极具代表性的候选者：ResNet-50 卷积神经网络，以及基于 Transformer 架构的轻量级模型 BERT-Tiny 与 MobileBERT。

### **3.1 计算机视觉候选者：ResNet-50**

ResNet-50（Residual Network）自 2015 年提出以来，凭借其残差连接（Residual Connections）成功解决了深度网络的梯度消失问题，已成为评估硬件推理性能的工业界绝对基准（De facto Benchmark）。

- **参数量与内存预估**：ResNet-50 的总参数量约为 2550 万。在标准 32 位单精度浮点数（FP32）格式下，其静态权重文件占用约 98 MB 的存储和内存空间。在 Batch Size = 1 的推理过程中，其特征图（Activations）的峰值内存占用通常在 50-100 MB 之间。这样的内存足迹（Memory Footprint）使得它在 7.5GB 的沙盒中运行游刃有余。

- **计算特征（Compute-bound）**：ResNet-50 的网络主体由密集的 $3 \times 3$ 和 $1 \times 1$ 卷积层构成。卷积操作具有极高的数据复用率（Data Reuse），即同一个卷积核权重会被滑动应用到输入特征图的多个位置。这种特性赋予了 ResNet-50 极高的算术强度（Arithmetic Intensity，即每字节内存访问对应的浮点运算次数）。单次前向传播大约需要进行 4.0 GFLOPs（十亿次浮点运算）。因此，ResNet-50 是一个典型的**计算密集型（Compute-bound）**模型。在 CPU 推理时，它的瓶颈通常在于 AVX-512 VNNI 单元的吞吐极限，而不是内存带宽。

### **3.2 自然语言处理候选者：轻量级 BERT 变体**

Transformer 架构与 CNN 有着截然不同的执行剖面（Execution Profile）。自注意力机制（Self-Attention）需要计算庞大的 Query ($Q$)、Key ($K$) 和 Value ($V$) 矩阵，这涉及大量的大型矩阵乘法。更关键的是，Transformer 在处理序列数据时，内存访问模式往往是扁平且缺乏复用性的，这使其更容易受到内存带宽的限制。标准版 BERT-Base 拥有 1.1 亿参数，占用约 440 MB 静态内存，在仅有 2 核的 CPU 上运行极度缓慢且占用过大，可能掩盖微架构层面的微妙变化。因此，我们考察以下两种广泛使用的轻量化变体。

#### **3.2.1 BERT-Tiny (TinyBERT-4)**

BERT-Tiny 是通过极致的知识蒸馏（Knowledge Distillation）技术大幅压缩而来的模型。

- **参数量与内存预估**：它仅保留了 4 层 Transformer 编码器，并将隐藏层维度大幅缩减，参数量锐减至 1450 万，静态内存占用仅约 55 MB。

- **计算特征**：其单次推理计算量仅约为 1.2 GFLOPs，推理速度比 BERT-Base 快 9.4 倍。

- **劣势分析**：正是由于 BERT-Tiny 过于轻量级且计算量过小，在 2 核 Cascade Lake 上，单次推理时间极短。这导致它在操作系统的时间片轮转中往往能"见缝插针"地执行完毕，对于旨在捕捉稳定 P99 长尾延迟的实验而言，BERT-Tiny 的退化表现可能过于剧烈且充满随机性，缺乏可重复的统计学说服力。

#### **3.2.2 MobileBERT**

MobileBERT 是 Google 专门为资源受限的移动端和边缘计算设备设计的深度压缩模型，采用了独特的倒置瓶颈（Inverted Bottleneck）架构。

- **参数量与内存预估**：MobileBERT 拥有 2530 万参数，静态内存占用约 100 MB。完全满足 7.5GB 的系统约束。

- **计算特征（Memory-bound 陷阱）**：尽管 MobileBERT 是 BERT-Large 的"瘦身版"，且计算速度比 BERT-Base 快 5.5 倍，但其倒置瓶颈设计为了弥补模型缩小带来的特征表达能力损失，在网络中间层生成了维度被严重放大的瞬态激活值（Inflated Intermediate Activations）。这意味着在执行自注意力计算和前馈神经网络（FFN）映射时，CPU 必须频繁且大量地读写这些膨胀的特征图。相较于卷积网络的局部性复用，MobileBERT 的内存读写模式呈现出极度依赖内存带宽（Memory Bandwidth）的倾向。因此，MobileBERT 被定性为高度**内存带宽密集型（Memory-bound）**的测试基准。

基于大量权威性能评测，下表对三种候选模型的核心特征进行了直观对比：

| **评估指标 (Metric)** | **ResNet-50** | **MobileBERT** | **BERT-Tiny** |

## **4. 故障敏感度与理论退化分析 (Sensitivity Hypothesis and Theoretical Degradation)**

本次动机实验（Motivation Experiment）的灵魂在于证明：当节点发生局部资源争抢时，哪怕 HAProxy 显示系统存活，DNN 的 P99 延迟也会彻底崩溃，完美演绎"灰色故障"。本节将从计算机微体系结构的核心机制出发，深度推演当我们使用 stress-ng 在后台注入不同类型的干扰时，推荐的模型会发生怎样的延迟退化。

### **4.1 威胁模型：stress-ng 的工作机制**

stress-ng 是一款专业的系统压力测试套件，能够精准地对 CPU、内存、缓存及操作系统内核接口施加极限负载。针对我们的实验，主要利用以下两种干扰原语（Stressors）：

1. **缓存摧毁者 (stress-ng --cache N)**：启动 $N$ 个工作进程，执行大范围、随机的内存读写操作，其唯一目的是使得 CPU 缓存（特别是 L3 Cache）产生颠簸（Thrashing）。

2. **算力吞噬者 (stress-ng --matrix N 或 --cpu N)**：启动 $N$ 个进程，持续执行浮点矩阵乘法运算或复杂的数学变换，从而榨干 CPU 的浮点运算单元（FPU）及算术逻辑单元（ALU）。

### **4.2 L3 Cache 颠簸与内存带宽争抢带来的延迟雪崩**

在现代 CPU 架构中，计算单元的速度远超内存数据的传输速度，因此构建了多级缓存（L1/L2/L3）来掩盖动态随机存取存储器（DRAM）的访问延迟。从微架构层面看，命中 L1 缓存通常只需 4-5 个时钟周期，L2 约 12 个周期，L3 约 40 个周期；而一旦发生缓存未命中（Cache Miss），CPU 必须通过内存总线访问 DDR4 DRAM，其延迟将暴增至 200 个时钟周期以上。

我们可以将 DNN 单次推理的总延迟 $T_{inference}$ 抽象为纯计算时间 $T_{compute}$ 和内存访问时间 $T_{memory}$ 的总和：

$$T_{inference} = T_{compute} + T_{memory}$$

其中，内存访问时间 $T_{memory}$ 极度依赖于缓存命中率 $h$：

$$T_{memory} \propto N_{accesses} \times \left( h \cdot L_{cache} + (1-h) \cdot L_{DRAM} \right)$$

**对 MobileBERT 的灾难性打击预测（The MobileBERT Trap）**：

如前文所述，MobileBERT 是一个重度的 Memory-bound 模型。在无干扰的正常情况下，22MB 的 L3 Cache 足够容纳 MobileBERT 的静态权重和大部分临时激活值，缓存命中率 $h$ 极高，$T_{memory}$ 维持在较低水平。

当我们在后台启动 stress-ng --cache 2 时，情况将发生根本性逆转。stress-ng 会生成无意义的垃圾数据，疯狂地向内存地址中写入。由于 Cascade Lake 的缓存替换策略（通常为伪 LRU 算法），stress-ng 占据了大量的缓存行（Cache Lines），无情地将 MobileBERT 原本驻留在 L3 Cache 中的权重和膨胀的特征图（Inflated Activations）驱逐出境（Eviction）。

此时，MobileBERT 在执行每一层注意力计算时，都会遭遇灾难性的 L3 Cache Miss。CPU 不得不通过有限的内存通道去远端 DRAM 抓取数据。更为致命的是，Transformer 的注意力机制涉及大范围的非连续内存访问，这会导致转换后备缓冲器（TLB）也发生严重的未命中（TLB Miss）。在 $L_{DRAM} \gg L_{cache}$ 且 $h \to 0$ 的数学规律下，MobileBERT 的 $T_{memory}$ 将呈指数级膨胀。**我们预测，在此压力下，MobileBERT 的 P99 延迟将发生戏剧性的恶化，可能会激增 10 倍到 20 倍以上，彻底跌出任何可接受的 SLO 阈值。这种由于纯微架构级缓存争抢导致的性能坍塌，HAProxy 完全无法感知（TCP 健康检查不会涉及大量内存读写），这正是教科书般的"灰色故障"**。

### **4.3 上下文切换与 AVX-512 FPU 饥饿**

除了内存子系统，CPU 的核心计算流水线同样脆弱。当使用 stress-ng --matrix 1 或 --cpu 2 注入压力时，干扰从缓存层面转移到了操作系统的调度和物理执行单元。

在 2 核的系统中，Triton Server 默认需要完整的 CPU 资源来并行化张量计算。当 stress-ng 启动时，Linux 的完全公平调度器（Completely Fair Scheduler, CFS）被迫在 Triton 工作线程和 stress-ng 线程之间进行频繁的时间片轮转（Time-slicing）。

**对 ResNet-50 的精准打击预测**：ResNet-50 作为典型的 Compute-bound 模型，其卷积计算极度依赖 Intel CPU 的 AVX-512 VNNI 指令集和浮点运算单元（FPU）。上下文切换对于使用 512 位超宽向量寄存器的进程而言，代价是极其高昂的。每次切换不仅需要保存和恢复巨大的寄存器上下文，更破坏了 CPU 内部流水线（Pipeline）和指令预取（Instruction Prefetching）的连续性。

并且，stress-ng --matrix 本身就是在执行密集的矩阵乘法，它将直接与 ResNet-50 争抢那极为有限的 FPU 执行端口（Execution Ports）。这会引发严重的队头阻塞（Head-of-Line Blocking）。**我们预测，ResNet-50 会因绝对算力被剥夺和频繁的上下文切换惩罚，呈现出线性的中位数（P50）延迟增长，同时伴随剧烈的 P99 长尾延迟抖动。由于 ResNet-50 本身具备极强的数据局部性（Data Locality），它对 Cache 压力相对不敏感，但对 FPU 饥饿极为敏感。这为我们提供了从另一个微架构维度观测灰色故障的绝佳视角。**

### **4.4 差异性可观测性与 HAProxy 的盲区**

需要向教授着重强调的是，为何上述惨烈的退化在负载均衡器眼中是"隐形"的。

HAProxy 通常通过向目标服务器发送心跳探测（例如 HTTP GET /health 或 /ping）来判断节点是否存活。这种请求：

1. 不涉及复杂的矩阵运算，不需要获取 AVX-512 寄存器。
2. 数据量极小，完全装载在 L1 Cache 中，不受 L3 缓存颠簸的影响。
3. 执行路径极短，即使在 CFS 调度器的高压下，依然能在 HAProxy 设置的超时时间（如 2 秒或 5 秒）内迅速返回响应。

因此，控制面（Control Plane）看到了"一切正常"的幻象，而数据面（Data Plane）的推理业务已经陷入瘫痪。这完美契合了本项目所需展示的实验目标。

## **5. 工程落地性与部署可行性论证 (Engineering Deployability)**

出色的理论必须能够转化为无缝的工程实践。Triton Inference Server 提供了高度复杂的生态系统，为了在 7.5GB 内存的约束下确保模型能够稳定加载并通过标准化工具压测，我们必须对推理后端（Backend）、模型导出格式及压测工具进行严格筛选。

### **5.1 框架后端选择：坚决弃用原生 PyTorch，采用 ONNX Runtime**

Triton 支持多种深度学习框架作为底层执行后端（Backend），包括原生 PyTorch（LibTorch）、TensorFlow、TensorRT 和 ONNX Runtime。

在 7.5GB 的内存沙盒中，**我们强烈建议弃用 Triton 的原生 PyTorch Backend，转而采用 ONNX Runtime Backend**。原生 PyTorch 框架在 Triton 中初始化时，会引入极其臃肿的运行时依赖，并且倾向于采用激进的内存预分配策略（Memory Allocator Bloat）。生产环境的 Issue 报告表明，使用原生 PyTorch 作为后端的 Triton 实例，往往会出现严重的 CPU 内存泄漏和无意义的内存驻留，占用量常飙升至 16GB 甚至更高。在我们的 7.5GB 节点上，这几乎肯定会引发 OOM 崩溃，使得旨在展示"慢化故障"的实验提前流产变为"宕机故障"。

相比之下，ONNX Runtime（ORT）是微软开发的跨平台、高性能推理引擎，其 CPU 执行提供程序（Execution Provider）完全由优化的 C++ 编写，内存足迹（Memory Footprint）极其清晰和克制。ORT 还能在底层自动调用 MLAS（Microsoft Linear Algebra Subprograms），完美利用 Cascade Lake 的 AVX-512 指令集，确保在无干扰状态下达到最高的吞吐量基准。

### **5.2 模型导出与标准化兼容性**

ResNet-50 和 MobileBERT 在工程生态中拥有极佳的兼容性。两者都可以非常平滑地通过 PyTorch 的 torch.onnx.export 接口转换为标准的 .onnx 格式。

**工程避坑指南**：在导出时，务必将 opset_version 设置为 14 或更高，并**强制固定输入张量的形状（Static Input Shapes）**（例如，固定 Batch Size 为 1）。动态轴（Dynamic Axes）会导致 ONNX Runtime 在每次推理时都重新分配内存并调整计算图，引入额外的 CPU 开销和内存碎片，这会严重污染我们对 P99 延迟测量的准确性。

### **5.3 标准化压测数据的准备**

为了向教授提供具有学术公信力的报告，我们不能使用随机噪声（Dummy Data）进行压测，必须采用标准的公共数据集形态来驱动 Triton 的 Perf Analyzer（perf_analyzer）。

- **对于 ResNet-50 (CV)**：应构造形状为 $[1, 3, 224, 224]$ 的 FP32 张量，模拟 ImageNet 数据集的标准输入尺寸。

- **对于 MobileBERT (NLP)**：应准备代表性的 GLUE (General Language Understanding Evaluation) 基准测试数据集或 SQuAD 的文本，使用预训练的分词器（Tokenizer）将其转换为固定序列长度（例如 Sequence Length = 128 或 512）的 INT64 token ID 数组。

perf_analyzer 能够以 gRPC 或 HTTP 协议向 Triton 发送这些格式化数据，精确捕获服务器端的排队延迟、计算延迟，并自动计算 P50、P90、P99 等关键百分位指标。这构成了我们观测灰色故障的"透视镜"。

## **6. 最终推荐与 Triton 部署规格 (Final Recommendation & Deployment Specifications)**

基于对硬件限制的敬畏、对微架构敏感度的深度推演以及对工程落地可行性的验证，本报告得出最终的行动指南。

### **6.1 首席学者最终推荐**

为了打造最完美、最具科学说服力的 Motivation Experiment，我强烈建议采取**"双模型对照组"部署策略**，同时引入 **ResNet-50** 和 **MobileBERT** 作为基准模型。

- 选用 **ResNet-50** 以展示 **"算力剥夺型灰色故障"**：它是一个极其稳定的 Compute-bound 基准。通过注入 stress-ng --matrix，教授将清晰地看到，当 CPU 浮点运算单元被挤占、上下文切换剧增时，DNN 推理延迟是如何随之恶化的。

- 选用 **MobileBERT** 以揭示 **"缓存颠簸型灰色故障"**：这是本实验的"杀手锏"。由于其倒置瓶颈带来的巨量中间激活值以及 Attention 机制对内存的极度依赖，MobileBERT 是一个完美的 Memory-bound 陷阱。当注入 stress-ng --cache 时，它将展示出令 HAProxy 彻底失明的灾难性 P99 延迟崩溃，完美切中研究主题。

这种双维度的展示方式，将向评审委员会证明，我们在分布式集群中捕获的灰色故障并非特定网络架构的偶然现象，而是深度学习负载与现代 CPU 内存层次结构及调度机制交互时普遍存在的系统性漏洞。

### **6.2 严密的 Triton 部署参数规格**

为了确保实验变量被严格控制，Triton Inference Server 的 config.pbtxt 必须采用以下防御性与针对性并存的配置：

**1. 锁定批处理规模 (Batch Size)**

建议将 Batch Size 严格固定为 **1**（即 max_batch_size: 0）。

*论证*：Triton 自带的动态批处理（Dynamic Batching）机制为了提高吞吐量，会主动引入等待和排队时间（Queue Delay）来聚合请求。这种人为的延迟将完全掩盖微架构层面的干扰，破坏实验的因果关系。固定 Batch Size 为 1 能确保测量的完全是纯粹的端到端硬件执行时间。

**2. 指定最优推理引擎 (Backend)**

必须显式指定使用 **ONNX Runtime**。

*论证*：绝对规避 PyTorch 原生后端的内存膨胀风险，将其锁定在安全的 7.5GB 内存边界内。

**3. 控制底层线程并发 (Threading Control)**

这部分配置对于单节点 2 核系统至关重要，必须在模型配置文件中显式干预 ORT 的线程行为：

```protobuf
backend: "onnxruntime"
max_batch_size: 0

instance_group [
  {
    parameters: {
      key: "intra_op_thread_count"
      value: { string_value: "2" }
    }
    # 关键设置：算子内并行线程数设为2。
    # 使得模型在无干扰时能完美吃满2个物理核心，达到性能峰值。
    # 一旦stress-ng介入，争抢将立刻白热化，导致严重的Head-of-Line阻塞。
  }
]

parameters: {
  key: "execution_mode"
  value: { string_value: "1" }
}
# 设为 ORT_SEQUENTIAL (对应值1)。
# 强制图节点串行执行，避免由于分支过多而生成不可控的 inter_op 辅助线程，
# 从而防止由于框架自身的线程管理混乱导致的延迟抖动，确保基线纯净。
```

**4. 压测实施路径建议**

在汇报演示时，应采取如下标准化流程以增强说服力：

1. **稳态捕获**：使用 perf_analyzer -m [model] --concurrency-range 1 获取无干扰环境下的基线 P50 和 P99 延迟。此时 P99 曲线应呈现平滑收敛态。

2. **算力剥夺演示**：启动 stress-ng --cpu 2。通过 perf_analyzer 观测 ResNet-50 延迟的线性上升。同时展示 HAProxy 的管理面板，证明该节点并未被剔除。

3. **内存海啸演示**：停止之前的干扰，启动 stress-ng --cache 2 猛烈攻击 L3 Cache。此时聚焦于 MobileBERT，展示其 P99 延迟如何出现数量级的暴涨，完成致命的"灰色故障"重现。

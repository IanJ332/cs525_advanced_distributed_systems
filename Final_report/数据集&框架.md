# GrayPulse 比较评估与数据集规划报告

## 系统背景与约束

灰度故障不是"宕机停止"类事件；它们是"隐蔽"的性能降级（例如，严重的性能下降、不稳定的I/O、容量压力、间歇性丢包），这类故障可以逃避常规的故障检测器，但仍然会损害应用程序——通常表现为尾部延迟激增和级联效应。

这与您测量到的经验现象（P99延迟的"长尾爆炸"）相符，也与更广泛的"规模化尾部效应"观察一致：随着扇出/规模的增加，在小系统中可以忽略的罕见减速会主导端到端延迟，从而催生了"尾部容忍"技术。

您的比较评估有两个硬性约束，它们极大地影响了基线的选择：

- **不能修改内核/协议**。基线必须能够在 VM01 的 L7 负载均衡层实现，或通过用户空间的 Python 脚本实现。

- **集群资源严重受限**。集群由 20 个节点（2核，7.5GB RAM）组成，VM01 是主控制器。这意味着基线必须具有低开销（每个请求 O(1) 复杂度，最小的内存/状态，简单的计时器/计数器）。

因此，在这些约束下，最合理的基线是**应用层的"弹性原语"**和**"延迟感知的负载均衡"**策略。这些策略已在广泛部署的代理/服务网格中成为生产标准，并且有明确的文献描述。

### 基线 1: 超时 + 重试预算 + 断路器/驱逐 (TRi-CB)

#### 定义（形式化定义）

该基线结合了三种经典的应用层机制：

1. **每次尝试的超时**：通过将"非常慢"的请求转换为快速失败信号，来限制尾部延迟。

2. **有界的重试策略**（重试预算）：尝试从瞬时故障中恢复，同时避免引发重试风暴。

3. **断路器**：当故障超过阈值时"跳闸"，暂时阻止对不健康后端的进一步调用，为其提供恢复时间。

断路器的模式通常定义为：包装一个受保护的调用；监控失败次数；一旦失败次数超过阈值，断路器"断开"，随后的调用立即失败，而不尝试执行受保护的调用；稍后的"半开"试探可以判断恢复情况。
Envoy 类似地将断路描述为快速失败和背压，以避免资源浪费和级联问题。
Netflix 的 Hystrix 也描述了相同的动机：控制分布式服务依赖之间的交互，容忍延迟/故障，并阻止级联故障。

#### 状态与转换（后端本地，O(1)）

让每个后端 (i) 维护：

- state_i ∈ {CLOSED, OPEN, HALF_OPEN}

- open_until_i (单调递增的时间戳)

- 一个基于短时间窗口的滚动失败估算器：

  - 最简单的方式：最近 W 个请求中的 fail_count_i，或者

  - 指数加权移动平均失败率 p̂_i (存储开销更低)。

将失败定义为：超时、传输错误/重置、5xx（可选），具体取决于您在负载均衡器（LB）层能观察到的内容。Envoy 的异常检测区分了本地产生的错误（如超时/重置）和上游返回的错误，这在概念上对于日志记录和分析很有用，即使您实现自己的逻辑也是如此。

**跳闸规则示例：** 如果连续超时/错误 ≥ K，或者最近 W 个请求中的失败率超过 θ，则状态从 CLOSED → OPEN，并设置 open_until_i = now + T_eject。

**恢复：** 当 now ≥ open_until_i 时，允许少量"探测"请求（HALF_OPEN 状态）。如果探测成功，则状态转回 CLOSED；如果任何探测失败，则转回 OPEN，并对 T_eject 应用指数退避。

#### 重试预算（防止放大效应）

重试对于掩盖瞬时故障至关重要，但无限制的重试会使降级的系统过载（重试风暴）。Envoy 明确建议配置重试预算来控制并发重试。

在此基线中，建议实现：

- 每个请求最大重试次数 = 1（强烈建议，考虑到您受限的 CPU/网络环境）

- 一个全局/共享的重试预算限制器，例如：

  - "最多 B 个并发重试"（令牌/信号量），或

  - "重试 QPS ≤ ρ × 原始 QPS"（漏桶）。

#### 为什么这对 GrayPulse 来说是一个强有力的基线？

GrayPulse 的优势在于基于延迟统计数据的、具有滞回特性的稳定路由。而 TRi-CB 故意设计得更简单，且被广泛部署：它主要通过 (a) 使用超时限制延迟和 (b) 将流量从不反复超时的实例移开，来缓解尾部延迟。这是一个现实的基线，因为许多真实系统将"延迟异常"视为超时，然后应用断路/驱逐。

#### 如何在 VM01 上用 Python 实现（无需修改协议/内核）？

在 Python L7 "转发负载均衡器"中的实现草图：

1. VM01 运行一个与您现有客户端（Python HTTP 客户端或直接访问单个端点的性能分析器）兼容的 HTTP 端点。

2. 负载均衡器选择一个后端（i）（在非 OPEN 的后端中使用简单的轮询或随机选择）。

3. 它以每次尝试的超时时间将推理请求转发给后端（i）。

4. 如果失败且重试预算允许，则转发给另一个不同的后端（j）。

5. 根据结果更新每个后端的计数器和断路器状态。

**伪代码（逻辑导向，非特定框架）：**

```python
def choose_backend_TRiCB(backends, now):
    # 排除 OPEN 状态的后端
    eligible = [b for b in backends if now >= b.open_until]
    if not eligible:
        eligible = backends  # 优雅降级，避免完全不可用
    return random.choice(eligible)

def handle_request_TRiCB(req, now):
    b1 = choose_backend_TRiCB(backends, now)
    ok, rtt = try_forward(req, backend=b1, timeout_ms=TIMEOUT_MS)
    record(b1, ok, rtt, timed_out=not ok)
    if ok:
        return response
    
    # 检查重试预算和请求截止时间
    if retry_budget.try_acquire() and within_deadline(req):
        # 选择与 b1 不同的后端
        b2 = choose_backend_TRiCB([b for b in backends if b != b1], now)
        ok2, rtt2 = try_forward(req, backend=b2, timeout_ms=TIMEOUT_MS)
        record(b2, ok2, rtt2, timed_out=not ok2)
        retry_budget.release()
        return response_if_ok_else_error()
    else:
        return error()
```

#### 资源适配性（2核控制器，20个后端）

该基线可以实现为：

- O(#后端) 内存消耗。

- 稳态下每个请求 O(1) 的工作量。

- 不需要跟踪分位数——只需要计数器/指数加权移动平均。

- 即使遥测数据有噪声，行为也稳定（超时是粗粒度但开销低的信号）。

### 基线 2: 二选一 + 峰值指数加权移动平均延迟感知负载均衡 (P2C-PEWMA)

#### 定义（形式化定义）

该基线是一种延迟感知路由策略：它将每个请求路由到估计具有最少待处理工作的后端，其中"待处理工作"通过观测到的往返时间（RTT）和队列深度（未完成请求数）的函数来近似。

两个关键成分已在生产系统中得到充分验证：

- **二选一采样**：选择 N 个随机后端（通常 N=2），然后从中选择最佳的一个。Envoy 在其最少请求负载均衡的文档中说明了这一点：选择 N 个随机主机（默认为 2），并选择其中活动请求数最少的一个。它明确称此为 P2C 并指出了其强大的性能特性。

- **峰值指数加权移动平均负载估算**：为每个后端维护一个对尖峰敏感的、类似指数加权移动平均的延迟估算器（"峰值"），然后乘以未完成请求数来估算工作负载。Linkerd 将"Peak EWMA"描述为维护每个副本 RTT 的移动平均值，并根据未完成请求数进行加权，然后路由到成本最小的副本。Tower 的 PeakEwma 文档更正式地阐述了相同的指标：预估工作 = 指数加权移动平均(延迟) × 未完成请求数，设计目的是对最坏情况下的延迟特别敏感，并且峰值会随时间衰减。Linkerd 的文档进一步阐述了基于指数加权移动平均的路由如何通过将请求发送到"最快的端点"来改善端到端延迟。

#### 模型与评分函数

为每个后端 (i) 维护：

- pending_i：当前处理中的请求数（派发时增加，完成时减少）。

- rtt_ewma_i：RTT 的峰值 EWMA 估算值。

- 如果没有历史记录，使用一个保守的默认 RTT（Tower 文档建议使用默认 RTT，以避免使未测量的端点过载）。

**评分：** score_i = rtt_ewma_i × (pending_i + 1)

**选择（P2C）：**

1. 均匀采样两个候选后端 (a, b)（或从非驱逐的后端中采样，如果您也维护一个最小的"失效"列表）。

2. 选择 i = argmin(score_a, score_b)。

**更新规则（峰值敏感）：** 使用衰减常数 τ 和单调时间 Δt。一种常见的峰值 EWMA 模式（符合"峰值随时间衰减"的概念）是： rtt_ewma ← max(rtt_sample, rtt_ewma ⋅ e^(-Δt/τ)) 这与 Tower 文档中描述的"对尖峰敏感，然后衰减"的行为一致。

#### 为什么这对 GrayPulse 来说是一个强有力的基线？

GrayPulse 基于鲁棒统计（Z-score/MAD）和滞回进行路由。P2C-PEWMA 是一个现实的竞争者，因为它是广泛部署的生产方法，仅使用 L7 可观测信号（RTT 和队列深度）就能将流量从缓慢的副本移开，并且它倾向于通过增加受影响副本的"工作"评分来快速响应尾部尖峰。

重要的是，与 TRi-CB 不同，它不需要将缓慢转换为超时；它会持续地将流量偏向于较慢的端点。

#### 如何在 VM01 上用 Python 实现（无需修改协议/内核）？

此基线非常适合 Python 负载均衡器，因为它只需要：

- 每个后端一个（原子操作）待处理请求计数器。

- 每个后端一个浮点数 RTT 估算器。

- 随机采样。

**伪代码：**

```python
def choose_backend_P2C_PEwma(backends):
    a, b = random.sample(backends, 2)
    return a if a.score() <= b.score() else b

class BackendState:
    def __init__(self):
        self.pending = 0
        self.rtt_ewma_ms = DEFAULT_RTT_MS
        self.last_update = monotonic_time()
    
    def score(self):
        return self.rtt_ewma_ms * (self.pending + 1)
    
    def on_start(self):
        self.pending += 1
    
    def on_finish(self, rtt_ms):
        self.pending -= 1
        # 峰值 EWMA：对尖峰敏感，随后衰减
        now = monotonic_time()
        decay = exp(-(now - self.last_update) / TAU_SEC)
        self.rtt_ewma_ms = max(rtt_ms, self.rtt_ewma_ms * decay)
        self.last_update = now
```

#### 资源适配性（2核控制器，20个后端）

P2C-PEWMA 是成本最低的延迟感知策略之一：

- O(1) 选择：两个随机样本 + 1 次比较。

- 每个后端状态最少（两个数字 + 一个时间戳）。

- 无需全局协调，无需复杂的统计计算。

#### 关于公平性的重要方法学说明

由于 GrayPulse 使用滞回和鲁棒的异常评分，而 P2C-PEWMA 纯粹基于延迟反馈，因此如果您同时报告稳定性指标（路由振荡、变动率），而不仅仅是尾部延迟，那么这种比较在学术上更有意义。

### ResNet-50（计算机视觉）：CIFAR-10 测试集，调整大小为 224×224

#### 数据集选择及为何符合约束条件

CIFAR-10 是标准的小型数据集：包含 60,000 张 32x32 的彩色图像，分为 10 类，其中测试图像 10,000 张。这满足了"必须是真实世界 + 轻量级"的要求，并且可以轻松缓存在 VM 磁盘上。

由于您部署的模型是 ResNet-50（通常在类似 ImageNet 的 224x224 输入上进行训练/评估），您可以使用 CIFAR-10 → 调整为 224x224 来产生真实的张量形状和可比较的计算量，而无需存储 ImageNet 验证集。（对于灰度故障防御的比较评估，输入形状/计算的真实性通常比标签保真度更重要。）

#### 预处理和张量规格（推荐默认值）

使用标准的 ResNet 预处理流程（由于 CIFAR 图像很小，可以简化调整大小/裁剪行为，但保持最终张量和归一化一致）：

1. 转换为 RGB 张量，缩放到 [0, 1]。

2. 使用 ImageNet 的均值和标准差进行归一化。

3. 输出张量：NCHW 浮点型，形状 [1, 3, 224, 224]。

PyTorch 的 ResNet 文档指出，预训练模型期望高度/宽度至少为 224 的 3 通道 RGB 图像；值缩放到 [0, 1]，并按均值 [0.485, 0.456, 0.406] 和标准差 [0.229, 0.224, 0.225] 进行归一化。Torchvision 的 ResNet-50 文档指定了调整大小 → 中心裁剪到 224 以及相同的归一化。

### MobileBERT（自然语言处理）：将 GLUE SST-2 句子作为真实的推理查询集

#### 数据集选择及为何符合约束条件

SST-2（斯坦福情感树库）是 GLUE 的一部分，广泛用于句子级分类，且体积小。TensorFlow Datasets 文档显示 GLUE/SST-2 的下载大小约为 7 MB，数据集大小约为 7 MB。这对于有限的磁盘/RAM 来说非常理想，并能产生真实的文本输入。

#### 下载/实现路径

- GLUE 基准测试规范参考：[https://gluebenchmark.com/](https://gluebenchmark.com/)（基准测试定义和任务列表）。

- 实用的下载包：glue/sst2 的 TensorFlow Datasets 条目 [https://www.tensorflow.org/datasets/catalog/glue（包含大小和任务描述）。](https://www.tensorflow.org/datasets/catalog/glue%EF%BC%88%E5%8C%85%E5%90%AB%E5%A4%A7%E5%B0%8F%E5%92%8C%E4%BB%BB%E5%8A%A1%E6%8F%8F%E8%BF%B0%EF%BC%89%E3%80%82)

#### 分词器 + 张量规格（推荐默认值）

MobileBERT 被明确定位为轻量级的 BERT 变体；Hugging Face 模型文档将其总结为为资源受限设备设计，并指出了实际的输入注意事项（例如，右填充）。

对于标准的 BERT 风格推理，您通常会发送：

- input_ids：形状 [1, L]，整数类型（在服务栈中通常为 int32）。

- attention_mask：形状 [1, L]，int32。

- token_type_ids：形状 [1, L]，int32（对于 SST-2 单句，可以全为 0；如果导出的模型需要，仍然包括）。

Hugging Face 分词器文档描述了分词器输出（BatchEncoding）包含模型输入，例如 input_ids 和 attention_mask。

**推荐的固定序列长度**：L = 128。这对于快速推理来说足够小，同时对于反映真实的句子多样性来说也足够大；它也避免了在 Perf Analyzer 中出现可变形状的复杂性。

#### 用于负载注入的载荷构建

- **选项 1（推荐用于 GrayPulse 和基线）**：Python 客户端 → VM01 负载均衡器。

  1. 预加载 SST-2 句子。

  2. 分词为固定长度的填充数组。

  3. 维护一个小池（例如，1k 个示例；SST-2 本身很小）。

  4. 向负载均衡器 POST 请求。

- **选项 2**：使用 JSON 数值列表的 Triton Perf Analyzer。与 CV 张量不同，文本标记张量很小，因此 JSON 数值列表是可行的（无需 base64）。Perf Analyzer 要求每个 "data" 条目包含单个批次的所有模型输入；张量必须按行主序展平（对于 [1, L]，这只是一个长度为 L 的列表）。

### 需要报告的核心指标（最小集）

为了使比较在学术上令人信服（而不仅仅是"单个 P99 点"），请报告少量指标，这些指标能够区分用户体验、系统效率以及控制正确性/稳定性。

#### 延迟分布（用户体验）

- 报告累积分布函数图以及百分位数：P50、P90、P95、P99，以及（如果稳定）P99.9，针对每种策略在相同负载和故障注入条件下。

- 包含针对固定延迟阈值 (D) 的服务水平目标达成率：延迟 ≤ D 的请求比例。SRE 指南将延迟和错误率视为关键服务水平指标，并强调使用聚合（如百分位数）来捕捉尾部。

#### 有效吞吐量（用户体验 + 效率）

- 当灰度故障导致尾部延迟激增和超时时，仅看吞吐量可能会产生误导。一个更强的指标是有效吞吐量，在 DNN 服务文献中定义为每单位时间内满足其服务水平目标截止时间的请求数。

- 对于延迟截止时间 D，操作上定义为：有效吞吐量 = #(成功且延迟 ≤ D 的请求) / 时间。这一点尤其重要，因为：

  - TRi-CB 可能通过超时慢请求（增加快速失败）来降低尾部延迟，这在延迟指标上看起来"好"，但在成功交付的工作量上却"差"。

  - GrayPulse 的价值主张通常在其能够增加在截止时间内完成且没有较大错误放大效应的请求比例时最强。

#### 错误率与超时率（可靠性）

- 跟踪：

  - 应用层成功率（2xx 与非 2xx 响应）。

  - 超时导致的失败（客户端或负载均衡器每次尝试的超时）。同样，错误率是标准的服务水平指标。

#### 控制正确性与稳定性（针对灰度故障）

- 由于您的系统明确检测并绕过灰度故障实例，请添加验证路由决策相对于已知真实情况（您注入的故障）正确性的指标：

  - **检测延迟/缓解延迟**：对于每个后端 (i) 上注入的灰度事件，测量：

    - 从注入开始到首次持续减少流向 (i) 的流量的时间。

    - 从恢复开始到重新接纳（流量恢复）的时间。

  - **误报率和漏报率**（针对缓解决策）：将缓解事件定义为"后端被降权/驱逐/绕过"。然后：

    - 误报率：在后端未处于注入降级状态时发生的缓解事件。

    - 漏报率：在后端处于注入降级状态期间错过的缓解事件。

  - 这就是 GrayPulse 的鲁棒统计 + 滞回应该能够比 P2C-PEWMA（基于反馈）和 TRi-CB（基于超时粗化）展现出更清晰的稳定性/正确性权衡的地方。

- **振荡/变动率指标**：统计：

  - 每分钟（或每 1k 请求）的路由变更次数。

  - 每个后端处于"断开"或"惩罚"状态的时间。

  - 在稳定条件下，每个后端的流量份额随时间变化的方差。

#### 防御成本（对公平性很重要）

- 像重试这样的基线可能会产生额外负载，必须加以衡量：

  - **请求放大因子**：放大因子 = 总后端尝试次数 / 前端请求数。带重试的 TRi-CB 应报告此项，以及重试预算饱和率（重试被阻止的频率）。Envoy 明确指出，重试预算设置可能过低（无重试）或过高（压垮服务），这强化了衡量这一维度的必要性。

- **控制器开销（VM01 CPU + 内存）**：报告：

  - VM01 上的负载均衡器 CPU 利用率。

  - 负载均衡器内存占用。

  - （可选采样）每个请求的开销。

  - 即使差异很小，报告它们也能加强 GrayPulse 在您严格的硬件约束下可部署的论点。

这套指标清晰地分离了"尾部延迟优势"与潜在隐藏成本（超时、重试、不稳定），这正是评审者在评估灰度故障缓解方案时通常会寻找的内容。

> 为了避免观测者效应（Observer Effect）和单点负载生成器瓶颈（Load Generator Bottleneck），我们将系统严格划分为三个物理平面：

1. **控制平面 (VM 01)**：仅运行 HAProxy 与 GrayPulse 路由决策进程，绝不存放任何数据集，以保证路由延迟的纯粹性。

2. **计算平面 (VM 05, 06...)**：仅运行无状态的 Triton 推理引擎。

3. **负载生成平面 (VM 02, VM 03)**：为了避免网络带宽和 I/O 成为压测瓶颈，我们采用了异构专用打流节点策略：

   - 征用 **VM 02** 作为专属的 **CV（计算机视觉）攻击机**，存放 3GB 的 CIFAR-10 分块张量数据。利用分块流式读取打破 CPU L3 Cache 的命中率造假。

   - 征用 **VM 03** 作为专属的 **NLP（自然语言处理）攻击机**，存放完整的 SST-2 语料库。这种数据物理隔离和单向数据流（Simplex Data Flow）设计，确保了压测数据的高度严谨性和统计学意义。

## 一、最终实验测试矩阵

我建议把 midterm 的实验矩阵固定为 4 组 campaign。这样既能回答"哪里崩"，也能回答"为什么崩"，还能回答"当前网关设计到底值不值"。

| Campaign | 目的 | 自变量 | 因变量 | 备注 |
|----------|------|--------|--------|------|
| A. 单工作负载基线扫描 | 找 CV-only 和 NLP-only 的各自拐点 | c_cv 或 c_nlp | P50/P95/P99、Goodput、错误率 | 先不混部 |
| B. 混部二维临界面搜索 | 找系统从稳态进入灰故障崩溃区的 frontier | (c_cv, c_nlp) | 同上 + 网关内部状态 | 核心图建议画成 heatmap |
| C. 近临界区稳定性/恢复性 | 看策略是否抖动、是否恢复慢 | (c_cv, c_nlp) 固定在 frontier 附近 ±10% | 震荡、恢复时间、错误放大 | 最能体现策略差异 |
| D. 网关架构对照 | 证明 byte-stream transparent forwarding 的价值 | Gateway=stream vs parse-json | CPU、RSS、网关排队、吞吐/Goodput | 路由固定为 RR |

### A. 单工作负载基线扫描

先分别让 VM02 单独打 CV-only，VM03 单独打 NLP-only。并发不建议线性细扫，而是先做**几何级数粗扫**：1, 2, 4, 8, 12, 16, 24, 32, ...，直到第一次出现连续窗口失稳。Google SRE 明确建议把延迟看成分布而不是均值，并强调高负载下常会出现 performance cliff；同时，Serving 系统仅看 throughput 不够，还要看满足时延目标的 goodput。

每个并发点统一采用三段式时间轴：

- warmup 30s
- steady/no-fault 60s
- gray-fault on 90s
- recovery 60s

这样同一轮实验里就同时拿到**稳态、故障、恢复**三段数据，不需要分三次跑。

### B. 混部二维临界面搜索

在得到单工作负载的 knee 之后，记为 K_cv 与 K_nlp。然后在二维平面上只扫一个**局部盒子**，不要全域暴力枚举。建议扫描：

- c_cv ∈ {0.5K, 0.75K, 1.0K, 1.25K, 1.5K}
- c_nlp ∈ {0.5K, 0.75K, 1.0K, 1.25K, 1.5K}

这给出一个 5×5 的混部热力图。对每个格点，分别运行 round_robin、tri_cb、p2c_pewma。如果 GrayPulse 很快接入，再把它作为第四列补上即可；如果 midterm 时还没接入，这个 3-policy 矩阵已经足够形成一版完整的 comparative evaluation。

### C. "崩溃点"正式定义

为了避免把偶然尖峰误判成崩溃，我建议把**崩溃临界点**定义为：

> 最小并发点 (c_cv, c_nlp)，使得在灰故障开启后，连续 3 个 5s 窗口同时满足：
> 1. P99 超过目标 SLO D；
> 2. Goodput 下降到 offered load 的 90% 以下；
> 3. 后端 pending/backlog 不再回落，而是单调或准单调上升。

这个定义把用户体验（P99）、有效服务量（goodput）和系统内部失稳（backlog runaway）绑在一起，比只报一个 "P99 爆了" 更像系统论文。SRE 对高分位延迟作为关键 SLI、以及使用多个 percentile 观察 tail behavior 有明确建议；SHEPHERD 则把 "单位时间内满足 SLO 的请求数" 作为 serving 系统的核心 goodput 指标。

### D. 近临界区细化搜索

在找到粗粒度 frontier 之后，只对 frontier 附近做**二分细化**。也就是对每条边界只继续搜索到"±1 并发 worker/task"的精度，而不是把整个二维平面细扫。这能把总实验轮数压下来，同时得到一条可发表的"崩溃边界曲线"。

我建议 midterm 图里最终至少给出三张核心图：

1. CV-only、NLP-only 的单负载并发扫描曲线；
2. mixed workload 的二维 heatmap（颜色 = P99 或 goodput）；
3. 近临界区的崩溃 frontier，对比三种路由策略。

## 二、p2c_pewma 的数据采集粒度

p2c_pewma 的学术价值不在于"它也把 P99 降了一点"，而在于它是否真的在**延迟变坏之前**已经对坏节点降权。官方实现文档把它定义得很清楚：Envoy 的 least-request 在等权情形下就是 P2C；Finagle/Tower 的 Peak-EWMA 则用**对峰值敏感的 RTT EWMA**乘上**outstanding/pending requests**来估计当前 work/load。

因此，网关侧不要只记"选中了哪个 backend"，而要把**决策前状态**也采下来。最小可用 schema 建议如下。

### 1) 每请求（per-request）日志

每个请求至少记录：

```
ts_ns
req_id
flow_type        # CV / NLP
payload_bytes
policy           # rr / tri_cb / p2c_pewma
backend_chosen
status_code
e2e_ms
upstream_ms
gateway_wait_us
retry_count
```

而对 p2c_pewma，再额外记录：

```
cand_a, cand_b
pending_a, pending_b
ewma_a_ms, ewma_b_ms
score_a, score_b
choice_margin = |score_a - score_b|
winner = argmin(score)
```

这里的 score 最好按你们实现里真实使用的形式直接落日志，不要事后重算。Tower 文档明确说 Peak-EWMA 的 load/work 是"EWMA(latency) × pending requests"；Finagle 文档也强调它对 RTT 峰值更敏感，并用 outstanding requests 做加权。

### 2) 每后端（per-backend）周期状态

每 100ms 或 200ms 做一次周期采样，记录每个 backend：

```
ts_ns
backend_id
pending
ewma_ms
current_score
req_rate_1s
timeout_rate_1s
error_rate_1s
bytes_out_1s
success_rate_1s
```

100–200ms 是个折中：足以看到 score/pending 的相位变化，又不会把日志量打爆。

### 3) 证明"预测性路由"最关键的 5 个派生指标

我建议 midterm 至少报以下 5 个派生指标，而不是只报原始 score 曲线。

**(a) Lead time（提前量）**

定义：某 backend 的 score_i(t) 首次超过阈值到其实际 P95/P99 latency_i 或 timeout rate 显著恶化之间的时间差。如果这个值为正，说明它不是被动地"看到 timeout 后才绕开"，而是提前感知到风险。

**(b) Rank correlation（排序相关性）**

在每个采样窗口，把所有 backend 按 score 排序，再按下一窗口的 realized median/P95 RTT 排序，计算 Spearman 或 Kendall 相关。这直接回答：score 到底是不是一个"可校准的坏节点排序器"。

**(c) Choice regret（选择后悔值）**

对每次 P2C 决策，定义 regret = realized_latency(chosen) - min(realized_latency among pair in next short window)。值越小越好。这比"平均延迟"更贴近 P2C 决策本身的质量。

**(d) Score oscillation（分数振荡）**

对每个 backend 计算 osc_i = mean(|score_i(t) - score_i(t-1)|)，再做全局平均和 95 分位。这个指标能直接看出近临界区是否发生"过敏式抖动"。

**(e) Traffic churn（流量抖动）**

固定窗口内，统计 backend 份额变化总量：churn = 0.5 * Σ_i |share_i(t) - share_i(t-1)|。如果 p2c_pewma 的 P99 好看，但 churn 明显高于 tri_cb，你们就可以诚实地说它更激进、更灵敏，但也更不稳。

### 4) p2c_pewma 最值得展示的两张图

如果只能放两张内部机制图，我建议：

- **图 1：某个故障 backend 的 pending / ewma / score / traffic share 四联时间线**
- **图 2：score rank 与 next-window realized latency rank 的相关性散点或箱线图**

这两张图最能说明"它不是随机绕路，而是依据可解释的预测信号在做决策"。

## 三、如何证明"字节流透传网关"优于"JSON 解析网关"

这部分一定要做成**独立 ablation**，不要和路由策略混在一起。否则 reviewer 会说你把两个变量一起改了。

### 1) 对照组定义

做两个 gateway 版本，其他一切保持一致：

**G1: Byte-stream transparent gateway**

当前 smart_gateway.py 路线：请求体不做 JSON decode，不 materialize 成 Python 对象，直接以流方式 forward。aiohttp 官方文档明确支持 streaming uploads，并说明可以在不把大文件读入内存的情况下发送；同时，StreamReader 支持 iter_chunked/iter_any 这类 chunk 级读取。

**G2: Traditional JSON parsing gateway**

在同样的 aiohttp 框架里，显式调用 await request.read() 或 await request.json()，然后再重序列化后发给上游。aiohttp 的 Request.read() 实现会把整个 body 逐块累积进 bytearray，而 Request.json() 先 text() 再 loads()；官方 quickstart 也明确提醒 read()/json()/text() 会把整个 body 载入内存。

### 2) 这个对照必须怎么跑

为了只比较"网关架构"，建议：

- 路由策略固定为 round_robin
- 后端固定为同一组健康副本
- 流量只用一种 payload（优先用你们现在的 600MB JSON chunk）
- VM02/03 并发脚本完全不变
- 上游模型和 fault injection 先关掉，做 gateway-only 开销测量
- 然后再在相同流量下打开灰故障，测"网关是否放大崩溃"

也就是说，先做 **gateway microbenchmark**，再做 **gateway-under-stress**。

### 3) 核心比较指标

我建议把这部分的指标压缩成 6 个，足够发表：

1. **Gateway CPU utilization**（进程级）
2. **Gateway RSS peak**
3. **Gateway overhead per request** = t_forward_start - t_accept
4. **Goodput**
5. **P99 end-to-end latency**
6. **CPU-seconds per GiB forwarded**（最能说明"2 核环境下谁更省"的指标）

如果你们用 Python 侧进程观测，psutil 官方文档支持直接读取进程 CPU 与 memory_info().rss；RSS 就是进程当前占用的物理内存。

### 4) 结果展示方式

这部分建议至少给一张表和一张图。

**表：Gateway-only 对照表**

列：Throughput / Goodput / CPU% / RSS peak / P99 / CPU-sec per GiB

**图：并发扫描曲线**

横轴：并发，纵轴：P99 或 Goodput，两条线：stream gateway vs parse-json gateway

如果做得漂亮，这一节可以独立得出一个很强的结论：

> 在 2-core 控制平面上，解析型网关把"payload 语义处理成本"引入了本不该成为瓶颈的调度层；而字节流透传将网关重新收敛为一个 I/O-bound forwarding element。

这个结论和 aiohttp 官方文档的行为模型是对齐的：streaming upload/forwarding 可以避免整包驻留内存，而 read/json/text 会把整包读入并解析。

## 四、我建议你们在 Midterm 里最终报告的指标集合

最后不要把指标铺得太散。Midterm 里我建议只保留下面这组"主指标 + 机制指标"。

**主指标**

- P50 / P95 / P99 / P99.9 latency
- Goodput
- Error rate / timeout rate
- Recovery time
- 崩溃临界点 (c_cv, c_nlp)

其中高分位延迟、错误率和吞吐本来就是 SRE 的核心 SLI；goodput 则更适合 serving 系统，因为它只计算满足时延目标的有效请求。

**机制指标（仅 p2c_pewma 与 GrayPulse 需要）**

- pending
- RTT-EWMA / score
- score lead time
- score-latency rank correlation
- score oscillation
- traffic churn

**架构指标（仅 gateway ablation 需要）**

- CPU%
- RSS peak
- gateway overhead
- CPU-sec per GiB forwarded
